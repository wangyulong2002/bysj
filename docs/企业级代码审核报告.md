## 0. 一句话结论

**这是一份"文档与自检意识已进入企业级、工程化与生产安全仍停在单人开发阶段"的项目。**

设计报告 12 万字、子任务清单 10 万字、专项测试报告 2.6 万字、174 个测试用例 —— 规格化程度超过 95% 的同类项目；但**没有 CI、没有容器化、没有独立测试环境、没有数据库迁移治理、HTTP 状态码被全局吞成 200、密码哈希强度比 Django 默认弱 100 倍、一键初始化脚本会在生产清空全库**。文档里写着的规范（"HTTP status + code 双层映射"、"DDL 权威"、"DDL 只作导出产物"）多处与代码实现相反。

**锐评**：这个项目最大的风险不是"不会写代码"，而是"写了很厚的规范文档，却没有用工程手段把规范钉死"。文档靠人遵守，代码靠机器执行 —— 前者一定会漂移。当前状态可交付演示、可答辩、可写进简历；**距离"敢让运维照着文档上线"还差一轮工程化补课**。

## 2. 先说做得对的（这决定后面批评的公允性）

这些不是客套，是真的踩过坑才会写出来的东西：

1. **对象级 ACL 与防 IDOR 是"服务端重算"而非"信任前端"**：`app/core/permissions.py:66` 的 `assert_owner`、`app/api/timetable.py:52` 的 `_resolve_class_id`（学生忽略入参 class_id、教师必须命中本人教学班、辅导员必须命中本人所带班级）—— 这是横向越权防护的正确姿势。
2. **文件上传三重校验**：扩展名 + MIME + magic bytes（`app/api/files.py:39-96`），存储名 UUID 化、拒绝 `..`/`/`/`\0`。多数同类项目只做扩展名。
3. **PII 合规有实现**：手机号默认脱敏返回、完整号码走独立权限点接口（`app/api/profile.py`）、RAG 日志对手机号/身份证正则脱敏、IP 只存"前 3 段+哈希"（`app/api/rag_chat.py:140-155`）。
4. **幂等做到了"MySQL 唯一表兜底 + Redis 快查"双通道**，并在业务执行**前**占位（`app/core/idempotency.py` `_db_reserve`），并发语义考虑到了 —— 这比"仅 Redis SETNX"成熟。
5. **降级矩阵有明确口径**（Redis 故障 → 登录锁定降级进程内、RAG 限流放行、幂等退 MySQL 直查），不是"一崩全崩"。
6. **RAG 有四级拒答闸门 + 离线评测集**：Recall@5=0.970 / MRR=0.939 / 误拒率 0/33，还有 88 条专项用例的测试报告。**多数团队的 RAG 连评测集都没有。**
7. **测试曾出事故并留下了技术护栏**：单测清空线上向量索引后，`vector_store._require_isolated_db()` 加上 `_test` 命名空间隔离（`tests/conftest.py`）—— 有复盘、有护栏，这是真实工程组织的特征。
8. **乐观锁 + 审计明细 + 快照固化**（成绩比例随记录固化，避免字典变更污染历史），死锁 1213 有识别与重试。

## 4. P0 · 阻断级问题

### P0-1 所有异常的 HTTP 状态码被吞成 200，监控直接失明

**位置**：`server/app/main.py:87-119`；`manage/apps/views.py:103-152`（`api_exception_handler`）

```python
# main.py:102-106  —— 数据库炸了也返回 200
@app.exception_handler(SQLAlchemyError)
async def sqlalchemy_handler(request, exc):
    logger.error("SQLAlchemy error: %s", exc, exc_info=True)
    return JSONResponse(status_code=200, content=fail(ErrorCode.SERVER_ERROR, "数据库操作失败"))
```

```python
# main.py:109-112  —— 404 / 405 也返回 200 + 业务码 5000
@app.exception_handler(StarletteHTTPException)
async def http_handler(request, exc):
    return JSONResponse(status_code=200, content=fail(ErrorCode.SERVER_ERROR, exc.detail))
```

**影响**：
- Nginx、云 WAF、CDN、APM、告警系统全部按 HTTP 状态码识别故障 —— 现在 500 也会被统计为"成功请求"，**故障静默**。
- 404 被映射成 5000"服务异常"，客户端无法区分"地址写错"与"后端崩了"。
- 与项目自己的规范**直接矛盾**：`app/core/errors.py:6-8` 白纸黑字写着"采用 HTTP status + code 双层映射（HTTP 4xx/5xx + 业务 code，见 6.1）"。

**锐评**：统一响应体（`{code,message,data}`）和统一 HTTP 200 是**两件事**。前者是契约，后者是反模式。为了前端"只解包一次"的便利，牺牲了整个运维观测链路 —— 这是典型的"以开发便利换运维成本"。

**修复方向**：保留业务 `code`，但 HTTP 状态码按语义返回（4001→400、4011→401、4031/4032→403、4091→409、4291→429、5xxx→500），前端 `request.js` 已能同时处理 HTTP 状态与业务码（`admin-web/src/utils/request.js` 已做了 `resp` 分支），改造成本很低。

### P0-2 密码哈希强度只有 Django 默认的 1/100，且注释写错了事实

**位置**：`server/app/core/security.py:52-66`

```python
def make_django_password(raw_password: str) -> str:
    """... 随机盐 16 字节（32 hex），迭代 10000（与 Django 默认一致）。"""
    iterations = 10000          # ← Django 5.2 默认是 1,000,000
```

**事实核对**：Django PBKDF2 默认迭代数演进为 3.2→260,000、4.2→600,000、**5.1/5.2→1,000,000**（Django 官方文档）。本项目 `requirements.txt` 要求 `Django>=5.2`，即基准是 1,000,000。硬编码 10,000 相当于把离线爆破成本降低 100 倍，**低于 OWASP 对 PBKDF2-SHA256 的最低建议（600,000）**。

**影响面**：`check_django_password` 会从存储串里读取实际迭代数，所以 **Django 侧创建的账号没问题**；但**所有走 FastAPI 侧改密/重置密码的用户**（`PUT /api/auth/password`，`app/api/auth.py:311`）落入 10,000 次哈希，成为密码库中最弱的一批 —— 攻击者只需要攻破最弱环节。

**锐评**：这不是"少写个零"的手误，是**注释里的"与 Django 默认一致"把错误固化成了"设计意图"**。以后没人会去质疑它。这是文档漂移造成安全债的标准案例。

**修复**：

```python
from django.contrib.auth.hashers import make_password, check_password  # 已是同库依赖

def make_django_password(raw_password: str) -> str:
    return make_password(raw_password)          # 永远跟随 Django 默认迭代数与升级策略
```

### P0-3 `init_db.sh` 是"清库脚本"，却叫"一键初始化（幂等，可重复执行）"

**位置**：`scripts/init_db.sh:6`（"幂等，可重复执行"）、`sql/init_all.sql:60` 起（业务表先 `DROP TABLE IF EXISTS` 再 `CREATE`）

```bash
# init_db.sh 注释
# 功能：执行一次完成全部初始化（幂等，可重复执行）：
#  ...
# 业务表 19 张（DROP+CREATE 重建，结构兼容 Django）
```

**影响**：运维/新同事看到"幂等、可重复执行"会认为"跑多少遍都没事"，于是在生产跑一次 → **21 张业务表全部清空，且脚本内没有任何备份步骤、没有二次确认、没有环境判定**。设计报告说"仅用于初始化环境"，但那句话在 125KB 文档的第 N 章，脚本本身没有护栏。

**锐评**：**"幂等"不等于"安全"。** 幂等描述的是"重复执行结果一致"，而这个脚本的一致结果就是"数据没了"。把破坏性脚本命名为 `init_*` 并分发给运维，是定时炸弹式交付。

**修复（三选一，建议全做）**：
1. 脚本入口加环境白名单：`[ "${APP_ENV:-dev}" = "dev" ] || { echo "拒绝在生产执行"; exit 1; }`；
2. 执行前强制 `mysqldump` 备份到 `BACKUP_DIR` 并打印备份路径；
3. 把"重建表"与"灌种子数据"拆成两个脚本，`init_db.sh` 只做 `migrate` + 建库。

### P0-4 数据库 DDL 双真相：migrations 与手写 SQL 并行维护

**位置**：`manage/apps/migrations/0001_initial.py` 等 4 个迁移文件 vs `sql/init_all.sql`（21 张表完整 CREATE TABLE）；`scripts/init_db.sh` **先 migrate 再跑 init_all.sql**

**事实**：项目声明"DDL 权威为 Django migrations（P0-1），sql/ 仅导出产物"，但：
- `sql/init_all.sql` 里的表结构是**人工维护的第二份真相**，没有任何自动导出机制；
- 迁移文件只有 4 个，而业务表有 21 张 → 后续字段变更靠"手改 SQL + 手改模型"，迁移链与 SQL 必然漂移；
- `init_db.sh` 的执行顺序是 `migrate`（建表）→ `init_all.sql`（**DROP 掉重新建**），等于**用 SQL 覆盖了 migrations 的产物**，正好把"权威"抹掉。

**影响**：两个环境的表结构差异无法自动检测；上线时"本地能跑、服务器报 Unknown column"是必然结局。

**修复**：二选一，并强制执行 —— ① 以 Django migrations 为唯一真相，`sql/` 改为 CI 中 `makemigrations --check` + `sqlmigrate` 自动导出，禁止手改；② 反之则删除 Django 的 DDL 能力，模型全部 `managed = False`，由 SQL 文件 + 迁移工具（Flyway/Alembic）管理。**现状是最坏的一种：两套都算数。**

### P0-5 测试直连共享 MySQL/Redis，且已经造成过生产事故

**位置**：`server/tests/conftest.py:56-70`（用 `settings.database_url` 直接连库并在真实 `sys_user`/`campus_file` 上增删）；`docs/overview.md` 记录：

> **高危发现 + 事故**：RAG 单测缺环境隔离，`test_full_rebuild` 直连真实共享 Redis，执行时清空了线上向量索引（chat 全部降级拒答）……

**现状**：
- ✅ **Redis 侧已修**：`_test` 命名空间 + `_require_isolated_db()` 护栏（做得好，值得肯定）；
- ❌ **MySQL 侧完全没修**：测试仍然跑在业务库上，`conftest` 会话夹具直接 `INSERT sys_user id=999999` / `DELETE campus_file`，没有测试库（无 `MYSQL_DB_TEST`）、没有事务回滚夹具、没有 fixture 隔离。

**影响**：174 个用例无法在 CI 中安全运行 → 也就**永远不会有 CI**（这是 P0-6 的直接因果）。

**修复**：`conftest` 里把 `MYSQL_DB` 指向 `campus_test`（启动时 `CREATE DATABASE IF NOT EXISTS` + `migrate`），并用 `transaction` fixture 每用例回滚；增加与 Redis 同款的"非测试库即抛错"护栏。

### P0-6 零 CI、零容器化、依赖不可复现

**证据**：
- 无 `.github/`、无 `Dockerfile`、无 `docker-compose.yml`（MySQL/Redis 靠口头约定"是 Docker 容器"）；
- 无 `ruff`/`flake8`/`mypy`/`eslint`/`prettier`/`.pre-commit-config.yaml`；
- `server/requirements.txt` 全部用 `>=` 下限、**无上界、无 lock 文件**，其中 `langchain>=1.0`、`langchain-openai>=1.0`、`numpy>=2.0`、`fastapi>=0.100` 都是大版本浮动；
- 部署文档把 `runserver` 与 gunicorn 并列为管理端部署选项（`docs/部署流程.md` §1）。

**影响**：
- 半年后重新 `pip install -r requirements.txt`，大概率装不上或行为不同（`langchain 2.x` 发布即爆）；
- 无 lint/类型检查 → `body: dict`、`except Exception` 这类问题只能靠人眼发现；
- 无容器 → "环境不就绪"永远是新同事第一天的主题；
- **上生产用 `runserver`** 是单线程开发服务器，任何并发都会成为事故。

**修复（最小闭环，1 天可完成）**：

```yaml
# .github/workflows/ci.yml —— 最小可用
on: [push, pull_request]
jobs:
  backend:
    runs-on: ubuntu-latest
    services:
      mysql: { image: 'mysql:8', env: { MYSQL_ROOT_PASSWORD: test, MYSQL_DATABASE: campus_test }, ports: ['3306:3306'] }
      redis: { image: 'redis/redis-stack:latest', ports: ['6379:6379'] }
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt ruff
      - run: ruff check server manage        # 先只挡明显错误，逐步收紧
      - run: pytest server/tests -q
```

配合 `pip-compile`/`uv lock` 固化依赖、`Dockerfile` 三行搞定可复现环境。

## 5. P1 · 严重问题

### 5.1 安全

**P1-1 双 JWT 体系无统一撤销，且 refresh token 存 localStorage**

| | FastAPI 应用端 | Django 管理端 |
|---|---|---|
| 签发密钥 | `JWT_SECRET` | `SECRET_KEY`（`simplejwt` 默认 `SIGNING_KEY`） |
| 失效机制 | `password_version` 自增（改密即失效）✅ | 无 blacklist、无版本位 ❌ |
| 有效期 | 2 小时 | access 2h / **refresh 7 天** |
| 客户端存储 | `uni.getStorageSync` | **localStorage**（`admin-web/src/utils/request.js:22`） |

**问题**：管理端改密/停用账号后，已签发的 access token 依然有效（simplejwt 只验签 + 查用户是否 active，不做版本比对）；`djangorestframework-simplejwt` 未启用 `token_blacklist` app → **refresh token 无法吊销，泄露即 7 天可控**；localStorage 存储意味着**任意 XSS（后台富文本公告是天然注入面）即可完整窃取长期凭证**。

**修复**：Django 侧启用 `rest_framework_simplejwt.token_blacklist` + `ROTATE_REFRESH_TOKENS`，在 `CustomUser` 加 `password_version` 校验（与 FastAPI 对齐），refresh token 改 httpOnly Cookie + `SameSite=Lax`；管理端公告富文本必须做过白名单消毒（`bleach`）后再入库。

**P1-2 全站明文 HTTP，无 TLS**

**位置**：`scripts/nginx/bysj.conf:19` `listen 80;` —— 整个文件没有 443、没有证书、没有 HSTS、没有 HTTP→HTTPS 跳转。

`manage/config/settings.py` 里倒是写了"HTTPS 反代支持（PUBLIC_BASE_URL 为 https 时自动启用 `SECURE_PROXY_SSL_HEADER`）"，**但 nginx 根本没配 HTTPS，这段代码在生产永远不会生效**。

**影响**：登录密码、JWT、学生个人信息、成绩全部明文过网（校园 WiFi 环境即可嗅探）。在等保/PIPL 语境下这是**一票否决项**。

**修复**：443 + Let's Encrypt（certbot）+ HSTS + 80 跳转；同时补安全响应头（`X-Content-Type-Options`、`X-Frame-Options: DENY`、`Referrer-Policy`、CSP）。

**P1-4 限流 fail-open + 计数键无 TTL 泄漏**

**位置**：`server/app/api/auth.py:58-73`、`server/app/core/login_lock.py:20-25`

### 5.2 数据一致性与并发

**P1-8 async 中间件做同步阻塞 I/O，并用 `time.sleep` 阻塞事件循环 3 秒**

**位置**：`server/app/core/idempotency.py:236-271`

```python
class IdempotencyMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        cached = redis_client.get(cache_key)     # ← 同步阻塞 I/O 在事件循环里
        ...
        db_resp = _db_lookup(biz_key)            # ← 同步 SQLAlchemy 在事件循环里
        ...
        for _ in range(30):
            time.sleep(0.1)                      # ← 阻塞事件循环，最长 3 秒
            existing = _db_lookup(biz_key)
```

**影响**：这个中间件挂在**所有 POST/PUT/PATCH/DELETE** 上（含文件上传、SSE 之外的写请求）。任何并发冲突都会让**整个进程的事件循环冻结 3 秒** —— 单 uvicorn worker 下，这是一个"一次请求打死全站"的 DoS 面。同步 Redis/SQLAlchemy 调用同理，只是冻得短一些。

**锐评**：项目在算法层面想得很周全（占位 → 轮询 → 冲突返回 409），但把异步框架当同步框架用，**所有并发设计都被这一行 `time.sleep` 抹平了**。

**修复**：
```python
await asyncio.sleep(0.1)
cached = await run_in_threadpool(redis_client.get, cache_key)
db_resp = await run_in_threadpool(_db_lookup, biz_key)
```
或改用 `redis.asyncio` + SQLAlchemy async engine。同时把"轮询 3 秒"改为"直接 409 + 客户端指数退避重试"。

**P1-9 成绩批量录入：逐条 `FOR UPDATE` + 无锁序 + 死锁靠重试兜**

**位置**：`server/app/api/score.py:254-350`

```python
with engine.begin() as conn:
    for item in scores:                       # 最多 200 条
        existing = conn.execute(text(
            "SELECT ... FROM campus_score WHERE student_id = :sid AND offering_id = :oid "
            "AND del_flag = '0' FOR UPDATE"), ...)         # ← 每条一次行锁
        ...
        conn.execute("UPDATE campus_score SET usual_score=... WHERE id=:id AND version=:v")
        if r.rowcount == 0: raise ConflictError(...)
        conn.execute("UPDATE campus_score SET version = version + 1 WHERE id = :id")  # ← 分两条
```

**三个问题**：
1. **锁粒度**：200 名学生 = 200 次加锁 + 一个长事务，锁持有时间随提交条数线性增长；`FOR UPDATE` 的加锁顺序取决于**前端提交顺序**（未按 `student_id` 排序）→ 两个教师同时提交不同顺序的名单，**死锁概率大幅上升**，项目自己的"1213 重试 3 次"就是给它兜底的。
2. **乐观锁被悲观锁架空**：`FOR UPDATE` 已经串行化了同一行的写，`version` 校验成了形式；更糟的是 `version+1` 是**独立第二条 UPDATE**，一旦有人删掉 `FOR UPDATE`（很自然的"优化"），就会静默丢更新。
3. **`updated` 语义含糊**：跳过（缺分、越界、不属于本班）只写进 `warnings` 文本，接口仍返回成功；若前端不展示 warnings，教师会以为全班录入成功。而一旦抛 `ConflictError`，**整个事务回滚**（200 条全废）。

**修复**：按 `student_id` 升序批量加锁（消除循环依赖）；单条 SQL 完成 `UPDATE ... SET version = version + 1 WHERE id=:id AND version=:v`；用 `INSERT ... ON DUPLICATE KEY UPDATE` 合并首录/修改两条路径；返回结构化 `skipped: [{student_id, reason}]` 而非纯文本警告。

**P1-10 排课冲突锁错了对象（并发双写窗口）**

**位置**：`manage/apps/views.py:170-215`

`_check_schedule_conflict()` 查询的是 `campus_course_schedule`（找重叠时段），而 `_lock_conflict_offering_rows()` 用 `SELECT ... FOR UPDATE` 锁的是 `campus_course_offering` 的行。

**问题**：锁的是 A 表记录，插入的是 B 表记录 —— 两个并发排课请求各自锁住不同的 offering 行集，**冲突检测与写入不在同一封锁范围**，InnoDB 无法阻止第二个请求在间隙中插入重叠 schedule。冲突检测与写入"同事务"只保证了原子性，**没有保证隔离性**。

**验证方法**：起 20 个并发请求对同一班级同一时段排课，观察是否出现 >1 条重叠记录。**修复**：改为用**数据库唯一约束**而不是应用层检索来保证互斥 —— 例如建"时间槽占用表"（`term + class_id + day_of_week + period_start` 唯一索引，插入冲突即视为排课冲突），或对 `campus_course_schedule` 建立覆盖该组合的唯一索引，让并发在数据库层被拒绝而不是靠 `SELECT FOR UPDATE` 兜。

**P1-12 业务编码用随机数生成（学号/工号/班级编码）**

**位置**：`manage/apps/serializers.py:32-41`

```python
def _gen_unique_code(prefix: str, qs, field: str, length: int = 6) -> str:
    chars = string.ascii_uppercase + string.digits
    for _ in range(30):
        code = prefix + "".join(random.choices(chars, k=length))   # ← 非加密随机 + check-then-act
        if not qs.filter(**{field: code}).exists():
            return code
    return f"{prefix}{int(time.time())}"                            # ← 兜底会撞
```

**问题**：
- **业务语义为 0**：学号应当是"入学年份 + 院系 + 专业 + 序号"，可排序、可核对、可与教务对接；随机 6 位后**人工无法校验、无法排序、无法按学号推断年级**；
- `random` 非加密安全的 `SystemRandom`，且是 check-then-act（并发下靠唯一索引兜）；
- 30 次重试耗尽后回退时间戳，**在同一秒并发生成必然唯一冲突**（且长度不一致）；
- 没有中心化的编码分配器 → 多实例部署时无法保证有序增长。

**修复**：建 `sys_code_sequence(prefix, year, last_value)` 表 + `SELECT ... FOR UPDATE` 或 Redis `INCR`；按业务规则拼装编码。

**P1-13 时间来源双轨：SQL `NOW()` 与 Python `datetime.now()` 混用**

- SQL `NOW()`：`auth.py:247,271,315`、`leave.py:142,308,324`、`message.py:101`、`profile.py:199`
- Python `datetime.now()`：`score.py:292`、`rag_chat.py:123`

**问题**：MySQL 容器时区（默认 UTC）与 Django `USE_TZ=False` + FastAPI 的 `datetime.now()`（本地时区）在**同一张表、同一逻辑时刻**写入两个不同基准的时间。跨时区部署或容器重建后，`create_time` 与 `update_time` 会错位 8 小时，且**没有任何机制能发现**（无约束、无校验）。

### 5.3 架构与性能

**P1-14 RAG Worker 跑在 Web 进程内（APScheduler）**

**位置**：`server/app/main.py:44-56`（lifespan 启动 `worker.start_scheduler()`）、`server/app/rag/worker.py`

**问题**：
- 多副本/多 worker 部署时**每个实例都会拉起调度器**。任务领取有 `UPDATE ... WHERE status=0` 抢占锁 ✅，但**全量重建标记、每日日志清理、崩溃恢复扫描没有分布式锁** → 重建会被触发多次；
- Embedding/LLM 长任务（单轮最多 20 个任务）跑在 **web 进程线程池**里，与用户请求争抢资源；`LLM_TIMEOUT_SECONDS=10` + 20 条/轮 ⇒ 最坏情况单轮占用 200 秒；
- 服务重启 → 调度中断（虽然 PROCESSING 超 10 分钟会重置，但任务延迟不可控）；
- 无法独立扩容：想让索引重建快点，只能扩 web 副本，代价是重复调度风险。

**修复**：拆独立 worker 进程（`python -m app.rag.worker`，不加 `--reload`），用 Redis 分布式锁（`SET NX PX`）守卫每轮调度；或引入 Celery/RQ/Arq 把"重建"这种长任务交给真队列。
