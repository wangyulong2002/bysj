## 2. 被测系统 RAG 架构（测试对象速览）

```
用户提问（游客，免登录）
   │
   ├─ ① 入参校验  question 非空 ≤500 字，session_id ≤64（4001）
   ├─ ② IP 限流   ≤10/min、≤100/day（4291，Redis 故障放行）
   ├─ ③ L0 输入闸门  越界关键词→out_of_scope；注入特征→unsafe（不检索不调 LLM）
   ├─ ④ 混合检索  向量 KNN(RediSearch HNSW COSINE) + BM25(title 单字 OR) → RRF(k=60) Top-5
   ├─ ⑤ L1 相关度闸门  best_sim 三档：≥0.75 正常 / 0.45~0.75 低置信 / <0.45 或 0 命中→no_context
   ├─ ⑥ LLM 生成  带引用编号 [1][2]（双通道：主→Agnes 兜底，双失败 5001 降级返回检索资料）
   ├─ ⑦ L2 领域围栏  哨兵 [[OUT_OF_SCOPE]] / [[NO_ANSWER]] → 拒答
   ├─ ⑧ L3 输出校验  引用越界清空、敏感内容→unsafe、弱相关附完整性提示
   └─ ⑨ 落库  campus_rag_log（IP 前缀+哈希、PII 脱敏、refuse_reason）
```

- 索引：Redis RediSearch `rag_idx`（DIM=2048，COSINE），实测 **26 个 chunk**，与 MySQL `campus_rag_chunk` 有效记录 **26/26 一致**。
- 实际运行模型（本次测试周期内）：生成 `doubao-seed-2.0-lite`；历史日志可见 `deepseek-chat`/`ark-code-latest`/`agnes-2.5-flash`（见 §5.7 配置漂移）。

## 5. 缺陷与发现（按优先级）

### 5.1 【中】L1 相关度阈值误拒：内容存在但 best_sim < 0.45

- **现象**："宿舍热水供应到晚上几点？"（评测集标注可答）→ 检索命中 5 片（其中 chunk 80583《学生宿舍介绍》正文明确含"热水"供应时间），但 `best_sim < RAG_SCORE_LOW(0.45)` → 模板拒答 `no_context`。DB 复核：`hit_count=5, refuse_reason='no_context'`。
- **根因分析**：
  1. 该问题为**内容级细节提问**，与 chunk 主题（宿舍整体介绍）的标题+正文向量相似度处于阈值之下；
  2. BM25 仅索引 **title** 字段（`vector_store.title_index_value`），"热水/供应时间"等内容级关键词**无法通过关键词路兜底**；
  3. 历史日志显示同题曾一次作答（弱相关档）、一次拒答，行为处于阈值边界不稳定。
- **影响**：误拒率上升，用户感知"明明有资料却答不知道"。
- **建议**：① 将 chunk 正文（或正文关键词摘要）纳入 BM25 索引（新增 TEXT 字段需评估 SCHEMA 变更与全量重建）；② 用 `scripts/rag_eval.py --calibrate` 在扩容后的评测集上重新网格标定阈值；③ 对"宿舍+设施名"类高频问法补充同义表述评测样本。

### 5.2 【中】弱相关档"语义拒答但契约未拒答"（L2 哨兵不稳定），且 L1 对无答案类拦截不足

- **现象**："学校毕业生就业率是多少？"（标注无答案）→ 检索命中 5 片、弱相关档调 LLM，模型按系统提示第 1 条输出"**暂无相关信息**"，但**未输出 `[[NO_ANSWER]]` 哨兵** → `refused=false`、`refuse_reason=null`，仅附完整性提示。C9（手机号补卡）同样命中该路径。
- **离线量化（逐条实测 best_sim）**：无答案类 8 条中仅 6 条被 L1 硬拦截（sim 0.279~0.391 < 0.45），**2 条穿透 L1 直达 LLM**："第三食堂什么时候开业？"（sim=0.464）、"研究生宿舍在哪个校区？"（sim=0.491）→ L1 硬拦截率 **0.75，低于设计意图 ≥0.9**。端到端 7/8 的"通过"实际依赖 LLM 低置信 Prompt + L2 哨兵兜底，不仅消耗 token（违背"L1 拦截不调 LLM 省成本"的设计收益），且兜底行为不稳定（就业率条目即兜底失败案例）。
- **根因**：
  1. 低置信 Prompt 存在双出口（第 1 条"如实回答暂无相关信息"与第 6 条"输出 [[NO_ANSWER]]"），模型无稳定偏好；接口层只识别哨兵，不识别"暂无相关信息"这一等价拒答文本；
  2. RAG_SCORE_LOW=0.45 对无答案类的区分度不足——知识库较小时（26 chunk），语义上"沾边"的无答案问题相似度普遍落在 0.45~0.75 区间。
- **影响**：无答案拒答准确率受损（0.875，目标 0.9）；`refuse_reason` 观测口径失真（8.7 拒答率统计偏低）；无答案问题仍消耗 2~5k token。
- **建议**：
  1. L3 增加后处理——答案清洗后若等于（或仅含）"暂无相关信息"/"暂无相关资料"等模板短语，转 `no_context` 拒答契约（`refused=true`）；
  2. 低置信 Prompt 消除双出口：资料不足时**只输出** [[NO_ANSWER]]，禁止输出"暂无相关信息"字样；
  3. 知识库扩容后用 `rag_eval.py --calibrate` 重新标定 LOW 阈值（本轮标定因 embedding API 429 限流未完成，需重跑）。

### 5.3 【中】多轮对话：检索侧未做上下文改写，指代追问必然低相似

- **现象**：session 内先问"图书馆几点开门？"（正常作答），追问"那它周末也开放吗？" → `no_context` 拒答。
- **根因**：历史轮次仅拼入**生成** Prompt（`_build_messages(..., history)`，T7-8），**检索仍用原始问题独立向量化**——"那它周末也开放吗"单独 embedding 后与任何 chunk 相似度极低，被 L1 拦截。历史根本没机会参与回答。
- **影响**：多轮体验（设计 8.1 加分项/8.5）在指代类追问上失效。
- **建议**：检索前增加**问题改写**步骤——用 LLM 或规则将指代追问与最近一轮问题合并为独立问题（"图书馆周末开放时间"）再向量化；或对追问类问题放宽 L1 阈值并强制携带上一轮 Top-N 片段。

### 5.4 【低】拒答路径 P95=2.72s 超设计 0.3s —— 设计口径与现实不符

- **实测**：L0 拒答（关键词命中，不检索）8~481ms，**达标**；L1 拒答（需 embedding + 混合检索后再判）1.4~4.7s，把整体拒答 P95 拉到 2.72s。
- **分析**：设计 8.4.1 的"拒答路径 P95≤0.3s"未区分 L0/L1；L1 路径含一次 embedding API 调用（约 1~3s），0.3s 目标在该链路下**物理不可达**。
- **建议**：修订验收口径为"L0 拒答 P95≤0.3s、L1 拒答 P95≤3s"；或在闸门前对 L1 判定增加 embedding 结果本地缓存（同问题哈希命中时跳过 API）。

### 5.5 【低】端到端 P95=9.50s 超设计 4s

- 与设计报告 8.6 注记一致（推理型生成模型单次 3~15s，P95≤4s 目标在该类模型下不达）。实测平均 3.10s、P95 9.50s、P99 14.39s，流式接口可显著改善首字感知延迟（C11 验证 SSE 正常）。建议按设计注记方案：切换非推理 `LLM_MODEL` 后重跑评测回归。

### 5.6 【高·工程】RAG 单元测试缺环境隔离，可在真实共享 Redis 上清空线上索引（事故记录）

- **经过**：本轮在 `server/venv` 执行 pytest 时，conftest 按默认配置连接了**真实共享的 Redis(6379)/MySQL(3307)**。`test_full_rebuild` 通过 `run_round()` 消费了真实的 `rag:rebuild_requested` 重建标记：清空 `rag_idx` 索引与全部 `rag:chunk:*` key，并以 **fake 向量**重建测试数据——导致线上 RAG 索引被清空，`/health` 的 rag_index 变为 NOT_CONFIGURED，问答接口全部降级为 `no_context` 拒答。
- **影响范围**：仅 Redis 向量索引与任务表（可重建数据）；MySQL `campus_rag_chunk`（26 行真实分片）、公告、知识库均完好，无用户数据损失。
- **恢复**：利用设计 8.3 的全量重建兜底机制——向 Redis 写入 `rag:rebuild_requested=1`，由运行中的 WSL worker（真实 embedding 环境）自动完成"清索引 → 重建 → 逐源真实向量化"，**约 20 秒后 num_docs=26 恢复**，问答验证正常。
- **根因**：conftest 未对 Redis 做测试隔离（`decode_responses` 文本客户端与 `vector_store.binary_redis` 均直连 db0）；涉及全量重建/清 key 的用例（test_full_rebuild、test_delete_task_removes_chunks 等）对共享环境有破坏性。
- **建议（按优先级）**：
  1. conftest 为测试进程固定独立 Redis 逻辑库（如 `REDIS_URL=redis://127.0.0.1:6379/15`），并强制覆盖 `vector_store.binary_redis` 与 `redis_client` 的连接；
  2. 或引入 fakeredis（支持 RediSearch 模拟）替换二进制客户端；
  3. 长期：CI 中默认 `RAG_WORKER_ENABLED=0`（已有）+ **索引写操作仅允许指向测试库**，任何 `FT.DROPINDEX`/`SCAN+DEL` 类操作前校验环境标记（如 `ENV=test` 断言）；
  4. 在 README/测试文档显著位置标注："运行 RAG 单测需独立 Redis 实例，禁止指向共享环境"。

### 5.7 【提示】模型选型三方不一致（设计 / 代码默认 / 运行时）

- 设计报告 8.2（v2.8）权威选型 `ark-code-latest`；`config.py` 默认 `deepseek-chat`；本轮运行时实际为 `doubao-seed-2.0-lite`（由 WSL 环境变量覆盖）。历史日志还出现过 `agnes-2.5-flash`（兜底通道生效过）。
- **建议**：在 `.env` 注释与部署文档中固化当前生效模型及依据，避免评测口径（提示词/引用/延迟）与实际模型脱钩；模型任何切换后按 8.7 回归纪律重跑评测集。
