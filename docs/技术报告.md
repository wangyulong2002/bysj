| 部署 | Nginx + Docker + systemd | — | 反向代理 / 容器化 / 进程管理 |

**总体架构**：

```
H5 / 微信小程序 / admin-web(Web)
        │
      Nginx :80（静态托管 + 反向代理）
   ┌────┴─────────┐
/api/**        /admin/**
   │              │
FastAPI:8000   Django:8001
   └──────┬───────┘
    MySQL:3307（campus 单库）
    Redis:6379（缓存+向量+限流）
          │
  火山方舟（LLM/Embedding）· Agnes（兜底）· 微信开放平台
```

**核心设计原则**：毕设规模下「组件尽量少、职责尽量清、契约尽量统一」——
- **单库共享**：FastAPI 与 Django 共用 campus 库，杜绝双库同步；
- **一库多用**：Redis Stack 同时承担缓存、限流、幂等、登录锁、向量检索五种职责；
- **一份配置**：根 `.env` 全端共享，改 `PUBLIC_BASE_URL` 一处即全端生效（9.3）；
- **统一契约**：全系统 `{code, message, data}` 响应格式与统一错误码（6.1）。

## 2. 后端技术：FastAPI 应用端

### 2.1 FastAPI + Uvicorn（Web 框架）

- **为什么选**：异步高性能（适合 SSE 流式问答）、基于类型注解自动生成 OpenAPI/Swagger 文档（`/docs` 交互调试）、与 Pydantic 深度集成实现声明式入参校验。
- **实际用法**：`APIRouter` 按模块拆分路由（auth/timetable/score/leave/message/profile/announcement/files/rag_chat/health）；`Uvicorn[standard]` 生产运行，多 worker 由 systemd 或 Nginx 负载。

### 2.2 Pydantic v2 + pydantic-settings（校验与配置）

- **入参校验**：所有请求体用 Pydantic BaseModel + `field_validator` 声明式校验，失败统一返回 `4001 参数错误`。例如 `ChatRequest` 限制 question 非空 ≤500 字、session_id ≤64 字符。
- **配置管理**：`Settings(BaseSettings)` 按「环境变量 > 项目根 .env」优先级加载，`@lru_cache` 单例；启动时校验必填项（MYSQL_PASS/JWT_SECRET 缺失拒绝启动）——**一份 .env 同时供 FastAPI、Django、前端构建注入**。

### 2.3 SQLAlchemy 2.x + PyMySQL（数据访问）

- **只读映射原则（P0-1）**：FastAPI 侧 ORM 仅做查询映射，**禁用 Alembic**——全库 DDL 唯一权威是 Django migrations，杜绝双头建表漂移。
- **连接池（C-05）**：`pool_size=10, max_overflow=20, pre_ping`；PyMySQL 驱动（Python 3.14 无 mysqlclient 预编译包，纯 Python 即装即用，`cryptography` 支持认证插件）。
- **使用模式**：`with engine.connect() as conn`（读）/ `engine.begin()`（事务写），SQL 用 `text()` 显式书写并参数化（防注入）。

### 2.4 redis-py ≥5.0（Redis 客户端）

- 双客户端设计：**文本客户端**（`decode_responses=True`，缓存/限流/幂等/登录锁）与**二进制客户端**（`decode_responses=False`，向量 float32 bytes 不能经文本编解码）严格分离。
- 所有 Redis 调用均带**故障降级**（见 §6.4 降级矩阵）。

### 2.5 PyJWT（签发）

- HS256 对称签名，Payload 含 `user_id / role_code / password_version / exp`；`password_version` 随改密自增，实现**改密后旧 token 全端失效**（T1-7）。
- 与 Django 侧 `rest_framework_simplejwt` 独立签发、互不冲突（应用端/管理端各自鉴权）。

### 2.6 APScheduler（进程内调度）

- `BackgroundScheduler` 承担两类后台任务：
  1. **RAG Worker**：每 30s 一轮（`max_instances=1, coalesce=True` 防重入），扫描 MySQL 任务表执行向量化；
  2. **日志清理**：每日 03:30 清理超过 `RAG_LOG_RETENTION_DAYS`(30 天) 的问答日志（C-06）。
- 测试环境 `RAG_WORKER_ENABLED=0` 关闭调度，避免 TestClient 拉起后台线程。
- **为什么不用 Celery/RQ**：任务量小（几十 chunk 级），MySQL 任务表 + 进程内调度足够可靠，少一个消息中间件运维成本（5.3.18 决策）。

### 2.7 核心自研横切模块（app/core/）

| 模块 | 职责 | 关键机制 |
|---|---|---|
| `response.py` | 统一响应 `{code, message, data}`，code=0 成功 | 全端契约一致（6.1） |
| `errors.py` | 统一错误码 + BizError 异常体系 | 4001/4011/4031/4032/4091/4291/5000/5001/5002 + 业务码（P2-21） |
| `security.py` | JWT 签发校验 + Django 密码哈希校验 + 文件签名 URL | 跨工程密码互认（管理端建的账号应用端能登录） |
| `permissions.py` | `require_role`（功能权限）+ `require_data_scope`（数据范围） | USER_SELF / TEACHING_SCOPE / COUNSELOR_CLASS_SCOPE / ALL 四档（3.5） |
| `idempotency.py` | 幂等中间件 | `Idempotency-Key` 请求头，Redis 缓存 + MySQL 唯一表双保险（P1-12） |
| `optimistic_lock.py` | 乐观锁工具 | version 字段 CAS 更新，冲突返回 4091（P1-09） |
| `login_lock.py` | 登录失败锁定 | 5 次失败锁 10 分钟；Redis 故障降级进程内计数（P0-4） |
| `middleware.py` | 请求日志 | 方法/路径/耗时/状态码，>1s 标记慢请求（可观测性） |
| `announcement_cache.py` | 公告版本化缓存 | `ann:version` 版本号失效，管理端发布即失效，TTL≤5min（P1-11） |

## 3. 管理端技术：Django 5.2 + DRF

### 3.1 为什么管理端用 Django 而不是继续 FastAPI

1. **migrations 即权威**：Django 的迁移体系天然承担「数据库 DDL 唯一权威」（P0-1），管理端是唯一建表入口，应用端只读消费；
2. **DRF ViewSet + Serializer**：管理端 12+ 个资源的标准 CRUD 用 ViewSet 几行搞定，开发效率远高于手写；
3. **5.2 LTS**：长期支持版，且是兼容 Python 3.14 的最低版本（A-01）。

### 3.2 关键集成点

| 技术点 | 实现 |
|---|---|
| **共享用户表（P1-8）** | `CustomUser(AbstractBaseUser)` 显式 `db_table='sys_user'`，与管理端建的用户账号在应用端可直接登录（密码哈希由 FastAPI 侧 `security.py` 兼容校验） |
| **统一响应（6.4）** | 自定义 Renderer（`apps/renderers.py`）把 DRF 输出改写为与应用端一致的 `{code, message, data}` |
| **管理前端托管（方案 2）** | 不用 Django Admin 模板；`/admin/` 路由直接返回 `admin-web/dist` 构建产物（AdminWebView），`/admin/api/**` 走 DRF + SimpleJWT |
| **业务联动** | 公告/知识库状态流转（`announcement_flow.py` / `knowledge_flow.py`）在**同一事务**内写 `campus_rag_task`，触发 FastAPI 侧 Worker 向量化（8.3） |
| **静态目录** | `STATICFILES_DIRS` 指向 admin-web 构建产物，`/static/assets/*` 由 staticfiles 服务 |
| **部署配置推导** | `ALLOWED_HOSTS`/`CSRF_TRUSTED_ORIGINS` 从 `.env` 的 `PUBLIC_BASE_URL` 自动推导（也可 `DJANGO_ALLOWED_HOSTS` 显式覆盖）；HTTPS 时自动启用 `SECURE_PROXY_SSL_HEADER`（9.4） |

### 3.3 管理端业务模块

DRF ViewSet 覆盖：院系、班级（含辅导员指定）、学生、教师、课程、学期（is_current 唯一切换）、教学班（course_offering）、排课（course_schedule）、成绩（发布/撤销写审计）、请假（管理视角）、公告（状态机流转）、知识库（content_hash 变更检测 + 整源重建）。

## 4. 前端技术

### 4.1 应用端：uni-app（Vue 2.6，CLI 工程）

- **为什么选 uni-app**：目标用户通过 **H5 与微信小程序**两类入口访问——uni-app 一套 Vue 代码编译双端，比分别开发 Web + 小程序节省一半以上工作量。
- **工程形态**：CLI 工程（`@dcloudio/uni-app 2.0.2` + `@vue/cli-service 5` + webpack5），`src/` 源码 → `npm run dev:h5 / build:h5 / dev:mp-weixin / build:mp-weixin`。
- **多端关键处理**：
  - API 地址由构建时环境变量 `VUE_APP_API_BASE` 注入（`utils/dev.js` 解析，缺失回退默认值）——配合 Makefile 实现「改一处 .env 全端生效」；
  - SSE 流式：H5 用 `EventSource`/fetch 流；小程序 `uni.request` 不支持 SSE，用 `enableChunked`（基础库 2.20+）；
  - WSL + Windows 微信开发者工具的产物同步（`scripts/sync-mp.sh --watch`，rsync 到 `D:\bysj-mp-weixin`）。
- **请求层**（`utils/request.js`）：自动携带 JWT、统一解析 `{code,message,data}`、401 跳登录、业务错误 toast。
- **页面（14 个）**：登录（账号密码+微信一键登录+游客入口）、首页、课表（周次切换双视角）、成绩查询/录入、请假申请/列表/审批、消息、个人中心/改密、公告列表/详情、AI 助手（流式渲染+引用卡片）。
- **设计体系**：「青岚校园 Teal Campus」（7.3）——SCSS 变量统一色板/圆角/阴影/缓动（`uni.scss`），双边框卡片、弱相关提示等交互细节全局统一。

### 4.2 管理端：admin-web（Vue 3.5 + Vite）

| 依赖 | 用途 | 选型理由 |
|---|---|---|
| Vue 3.5 | 视图框架 | Composition API + 性能；与 uni-app（Vue2）隔离，互不影响 |
| Vite + @vitejs/plugin-vue | 构建 | 毫秒级热更新，构建产物 `dist/` 交由 Django/Nginx 托管 |
| vue-router 4.5 | 路由 | 登录守卫（无 token 重定向登录页） |
| Pinia 2.3 | 状态管理 | Vue3 官方推荐，管理 token/用户信息 |
| Element Plus 2.9 | UI 组件库 | 管理后台标准组件（表格/表单/对话框），开箱即用 |
| axios 1.8 | HTTP | 拦截器统一注入 JWT、处理统一响应码 |
| sass | 样式 | 管理端主题变量（青岚 7.3.6） |

- **鉴权模式**：登录拿 SimpleJWT → axios 请求头携带 Bearer → 401 统一跳登录。
- **代理开发**：dev 模式 Vite proxy `/admin/api → Django:8001`，避免 CORS。

## 5. MySQL 数据库技术

### 5.1 基础约定

| 项 | 约定 | 理由 |
|---|---|---|
| 版本/部署 | MySQL 8.4，Docker 容器，端口 3307 | 与宿主环境隔离、可复现 |
| 字符集 | utf8mb4 + collation `utf8mb4_0900_ai_ci` | 完整 emoji 支持；排序规则全栈统一（B-10） |
| 引擎 | InnoDB | 事务 + 行级锁（乐观锁/幂等唯一键依赖） |
| 主键 | `id BIGINT AUTO_INCREMENT` | 分布式友好预留、索引顺序写入 |
| 时区 | Asia/Shanghai，USE_TZ=False（Django） | 全栈时间语义统一（B-10） |
| 删除 | `del_flag` 逻辑删除（0 正常/2 删除），外键 `ON DELETE RESTRICT` | 不物理级联删除，数据可追溯 |

### 5.2 表设计（campus 单库 22+ 表）

- **系统表 `sys_*`**（精简自建，不依赖若依）：`sys_user`（双端共享用户，P1-8）、`sys_dict_type/sys_dict_data/sys_config`。
- **组织**：`campus_department / campus_class（counselor_id 辅导员指定，每教师≤2 班）/ campus_student / campus_teacher`。
- **教学**：`campus_term（is_current 全库唯一，事务切换）/ campus_course / campus_course_offering（教学班）/ campus_course_schedule（排课）/ campus_score + campus_score_audit（成绩+审计）`。
- **事务**：`campus_leave（状态机）/ campus_message（站内信）`。
- **内容**：`campus_announcement（公告状态机）/ campus_knowledge（RAG 知识源）`。
- **RAG**：`campus_rag_chunk（分片，source_version 版本管理）/ campus_rag_task（任务队列）/ campus_rag_log（问答日志）`。
- **支撑**：`campus_file（文件+ACL）/ campus_idempotency_key（幂等唯一表）`。

### 5.3 数据库层的关键技术

1. **乐观锁（P1-09）**：成绩等并发更新携带 `version` 字段 CAS 更新（`UPDATE ... WHERE id=? AND version=?`），受影响行数=0 即冲突返回 `4091`——解决「教师 A/B 同时编辑同一成绩单」。
2. **幂等表（P1-12）**：`campus_idempotency_key` 唯一索引兜底；写接口带 `Idempotency-Key` 头，网络重试不产生重复数据；Redis 缓存命中直接返回原结果。
3. **同事务任务写入（P0-08）**：公告/知识库状态变更与 `campus_rag_task` 插入在同一事务——状态生效则任务必存在，不会丢向量化。
4. **唯一约束辅助业务**：`campus_term.is_current` 部分唯一思路 + 事务切换，保证任意时刻仅一个当前学期。
5. **备份策略（9.5）**：每日 `mysqldump --single-transaction` 全量，保留 `BACKUP_RETENTION_DAYS`，目标 RPO≤24h / RTO≤2h。

## 6. Redis 技术详解

选用 **Redis Stack**（含 RediSearch 模块）而非普通 Redis，核心动机：**向量检索能力内置**，避免再引入 Milvus/FAISS 独立向量库。一个 Redis 承担五种职责：

### 6.1 五类用途与 Key 设计

| 用途 | Key 模式 | 机制 |
|---|---|---|
| 公告热点缓存 | `ann:list:*` / `ann:detail:*` + 版本键 `ann:version` | 版本化失效：管理端发布时 `INCR ann:version`，旧缓存键自然失效；TTL≤5min（P1-11，最终一致） |
| 接口限流 | `rag:rate:{ip}:min` / `:day` | INCR+EXPIRE 滑窗计数：10 次/分钟、100 次/日，超限 4291（B-13 登录限流同机制 5 次/分） |
| 幂等缓存 | `idem:{key}` | Idempotency-Key → 响应体缓存 24h（`IDEMPOTENCY_EXPIRE_SECONDS`），MySQL 唯一表为准 |
| 登录失败计数 | 登录锁定键 | 5 次失败锁 10 分钟（`LOGIN_MAX_FAIL/LOGIN_LOCK_MINUTES`） |
| **向量索引** | `rag:chunk:{chunk_id}` HASH + `rag_idx` 索引 | RediSearch HNSW，见 §7 |

### 6.2 客户端与持久化

- 双客户端：文本（decode_responses=True）/ 二进制（向量 bytes），`socket_timeout` 3~5s；
- **持久化**：AOF（appendonly）+ RDB；数据卷挂载（`-v redis-data:/data`）——容器重建不丢向量（生产事故复盘后加固）；
- **索引一致性对账**：`rag_idx` num_docs 与 MySQL `campus_rag_chunk` 有效行数定期核对（专项测试 D4 用例）。

### 6.3 RediSearch 向量检索要点

- 索引 DDL（8.2 权威，字段不得增减）：`source_type TAG / source_id NUMERIC SORTABLE / title TEXT / chunk_index NUMERIC / embedding VECTOR HNSW TYPE FLOAT32 DIM 2048 DISTANCE_METRIC COSINE`；
- KNN 查询：`*=>[KNN $K @embedding $q_vec AS knn_score] DIALECT 2`（本环境实测须显式 `DIALECT 2` 且置于 PARAMS 之前，`SORTBY knn_score` 升序）；
- 中文 BM25 兼容：默认分词把整段中文当一个 token，**写入时对 title 附加「单字空格序列」**，查询侧按单字 OR 召回（实现约定，不改 SCHEMA）；
- **RediSearch 限制**：仅支持 db0 建索引（`Cannot create index on db != 0`）——单测隔离因此采用「索引/键命名空间」方案（`rag_idx_test`/`rag:chunk:test:`）而非独立逻辑库。

### 6.4 故障降级矩阵（9.7，不得混用）

| 组件 | 故障策略 | 一致性 |
|---|---|---|
| 业务数据 | MySQL 权威，不降级 | 强一致 |
| 公告缓存 | 直查 MySQL（穿透放行） | 最终一致（TTL≤5min） |
| 幂等键 | 降级 MySQL 直查，**不拒绝写** | 强一致（MySQL） |
| 登录失败计数 | 降级进程内计数（单实例有效） | 尽力一致 |
| RAG 向量索引 | 返回 **5002**「AI 助手暂不可用」，**不做假检索** | 强一致 |
| RAG 限流 | **放行** + 告警 | 尽力一致 |

## 7. RAG 智能问答技术

### 7.1 技术底座

| 组件 | 选型 | 说明 |
|---|---|---|
| 编排 | LangChain 1.0（自定义 `HybridRetriever(BaseRetriever)`） | 只用其 Retriever 抽象，不用内置 VectorStore，检索核心自研可控 |
| LLM 接入 | `openai` SDK（OpenAI 兼容）指向火山方舟 | 生成 `doubao-seed-2.0-lite`（轻量快速）；**兜底通道 Agnes `agnes-2.5-flash`**（ADR-013：主通道连接异常/429/5xx 同请求内自动切换，双失败才 5001；**仅生成兜底，Embedding 不兜底**防维度污染索引） |
| Embedding | `doubao-embedding-vision`（2048 维） | 与生成共用方舟端点与密钥；维度与索引 DDL 硬绑定（EMB_DIM） |
| 向量序列化 | numpy float32 → bytes | 直传 RediSearch |
| 知识源 | 已发布公告（source_type=1）+ 知识库（=2） | 管理端录入，状态变更驱动向量化 |

### 7.2 检索：混合检索 + RRF 融合

1. **向量 KNN 路**：问题 → embedding → RediSearch HNSW Top-10（COSINE 距离）；
2. **BM25 关键词路**：问题提取关键词（中文单字去停用字 + 英数词，≤24 个）→ `@title:(a|b|c...)` Top-10——兜底「XX 宿舍/教授姓名」类专有名词（标题命中但语义相似度低的场景）；
3. **RRF 融合**：`score = Σ 1/(60 + rank_i)`，同 chunk 双路命中得分相加，取 Top-5（`RAG_TOP_N`）注入 Prompt；
4. **回表**：chunk 正文存 MySQL `campus_rag_chunk`，命中后按 id 回表取 content/title/url（Redis 只存向量+元数据）；
5. **切分**：300~500 字、重叠 50~100 字（`chunker.py`），知识库富文本先剥 HTML。

### 7.3 四级拒答闸门（8.4.1，ADR-012）

| 层 | 时机 | 判据 | 动作 |
|---|---|---|---|
| **L0** | 检索前 | 越界意图/注入关键词表（`scope_keywords.py`，归一化匹配防拆字绕过） | 模板拒答 `out_of_scope`/`unsafe`，**不检索不调 LLM**（实测 8~481ms） |
| **L1** | 检索后 | `best_sim` 三档（`RAG_SCORE_HIGH=0.75 / RAG_SCORE_LOW` 可配置）+ **BM25 兜底豁免**（融合结果 BM25 命中排名≤`RAG_BM25_GATE_RANK` 时即使 sim 低也放行，防内容级提问误拒） | 低于阈值→`no_context` 不调 LLM；中间档→低置信 Prompt |
| **L2** | 生成时 | 系统提示领域围栏哨兵 `[[OUT_OF_SCOPE]]` / `[[NO_ANSWER]]`（低置信档 Prompt 单出口：资料不足只输出哨兵） | 命中转拒答契约 |
| **L3** | 生成后 | 引用编号越界 / 敏感词 / "暂无相关信息"等价文本 | 清引用降级 / `unsafe` / 统一转 `no_context` |

**统一拒答契约**：`code=0` + `data.refused=true` + `refuse_reason ∈ {no_context, out_of_scope, unsafe}`，**不新增错误码**；与限流 4291、5001、5002 互不替代。

### 7.4 工程化机制

- **向量化任务队列（P0-08/P0-09）**：`campus_rag_task` 表 + Worker 30s/轮。领取用条件更新（`UPDATE ... WHERE status=0` 受影响行数=1 才持有，防多 worker 重复消费）；失败指数退避 2/4/8 分钟、超 3 次终态 FAILED；PROCESSING 超 10 分钟崩溃恢复；**整源重建**：新版本 chunk 全部向量化成功后才删旧版本，避免新旧向量并存答案冲突；**全量重建兜底**：`rag:rebuild_requested` 标记 → 清索引 → 逐源重建（实测 20~45s 自愈 26 chunk）。
- **SSE 流式 + 多轮**：`/api/rag/chat/stream` 首帧前完成校验/限流/检索；增量 `delta` 帧 + 结束 `done` 帧（answer 为 L2/L3 清洗后**权威文本**，客户端以其覆盖流式累积）；多轮按 `session_id` 取最近 3 轮非拒答问答注入 Prompt，且**检索前做问题改写**（上一轮问题+当前问题拼接，解决"那它周末也开放吗"指代失联）。
- **引用溯源**：答案标注 `[n]`，L3 校验编号不越界，`sources` 由实际引用映射生成（公告带详情 URL）。
- **评测体系（8.7）**：57 条七类评测集 + 离线脚本 `rag_eval.py`（Recall@K/MRR/阈值标定 `--calibrate`）。实测：Recall@5=0.970、MRR=0.939、误拒率 0、越界拒答/注入拦截 100%；88 条专项端到端见《RAG专项测试报告》。

## 9. 部署与工程化

### 9.1 配置管理（9.3）

根 `bysj/.env` 为**唯一配置点**：`PUBLIC_BASE_URL` 一处修改，经 Makefile 构建注入前端（`VUE_APP_API_BASE`）、被 FastAPI/Django 直接读取——「改一处、重新构建、全端生效」。生产另强制 `DJANGO_SECRET_KEY`（缺失拒绝启动）、`DJANGO_ALLOWED_HOSTS`。

### 9.2 Nginx 入口（9.4）

```
/            → /var/www/bysj-h5 静态产物（try_files 兜底 index.html）
/api/**      → proxy_pass FastAPI:8000
/api/rag/chat/stream → 同上 + proxy_buffering off（SSE 必须）+ read_timeout 300s
/admin/**    → proxy_pass Django:8001
/static/**   → 磁盘命中优先，未命中回源 Django（管理前端 assets）
client_max_body_size 12m   # C-05：大于应用层 10MB，否则 413 先于业务校验
```

### 9.3 容器与进程

- MySQL/Redis：Docker 容器（**数据卷持久化** + Redis AOF，事故加固项）；
- FastAPI/Django：开发期 `make all`（setsid + 日志重定向），生产 systemd（`Restart=always`）或 Docker Compose（9.8 备选）；
- Makefile 一键编排：`make all / h5 / h5-build / mp-dev / mp-sync-watch / stop / status / logs / init-db / seed-demo`。

### 9.4 健康检查与观测（9.6）

`GET /api/health` 聚合四项：`app / mysql / redis / rag_index`（num_docs>0 且无 rebuilding 标记为 UP）；请求日志中间件记录慢请求（>1s）；RAG 任务失败数可从 `campus_rag_task.status=3` 观测。
